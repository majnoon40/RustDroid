## 2. P0/P1 — concurrency, teardown, process safety

### P0 — the I/O "owner thread" was not one (fixed, `ba46d17`)

Confirmed on inspection rather than inferred. Two independent defects:

1. `Dispatchers.IO.limitedParallelism(1)` limits *concurrency*; it does not
   confine a *thread*. `Dispatchers.IO` is an elastic pool, so successive
   dispatches can land on different workers — the class doc promised
   "exactly one thread ever performs them".
2. Worse, `closeSession` re-derived the limiter *per call* inside
   `ioScope.launch { withContext(Dispatchers.IO.limitedParallelism(1)) }`.
   `limitedParallelism` does not memoize — it returns a new view each
   invocation — so two concurrent `closeSession` calls received two
   independent parallelism-1 dispatchers and ran fully in parallel. The
   single-flight guarantee did not exist at all, on the exact path (master
   fd close) the teardown design exists to protect.

Fix: one `Executors.newSingleThreadExecutor` daemon dispatcher
(`rd-terminal-io`) stored in a field and never re-derived; the inner
`withContext` deleted. `closeSession` also removes the entry from
`_sessions` **before** enqueuing teardown, so a second tap cannot enqueue a
duplicate.

### P1 — non-atomic read-modify-write on shared state (fixed, `ba46d17`)

`_sessions` is written from three threads (create on main, close on the
owner thread, `updateEntry` from the vendored session's callback handler)
and all three did `value = value ± x`, which is not atomic across the read
and the write. Interleaved create+close loses an update — a resurrected
closed session (dead fd behind a live tab) or a vanished live session
(orphaned shell with no UI affordance). All three now use `update { }`
(CAS-looped). `views` is now a `ConcurrentHashMap`.

### P1 — `killpg` with a non-positive pgid + identity-guarded fallback (fixed, `df4e132`)

`killpg(0, sig)` is `kill(0, sig)` — the caller's OWN process group, i.e.
the app signalling itself. `killpg(-1, ·)` targets init. Neither is a
no-op, and both are reachable: upstream's `mShellPid` is 0 before start and
-1 after exit, so an already-finished session hands us a non-positive pid.

Per the maintainer's direction this is **not** refuse-and-log alone. The
master close's SIGHUP only reaches whatever occupies the pty's *current*
foreground process group at that instant, so a shell that backgrounded
itself, changed its own pgid, or whose *group* bookkeeping (rather than its
pid) is the stale part can outlive the hangup indefinitely. Since
`shellPid > 1` is independently known-good in that branch, the weaker
cleanup is not silently accepted:

- group signal gated on `shellPid > 1`;
- a direct SIGKILL to the shell follows, but **only** identity-guarded —
  PID **and** start time revalidated through the same single `readStat`
  observation every other signal path uses, and skipped for zombies. Not a
  raw pid signal.

The shell's identity is captured once at teardown start and reused for late
rediscovery and the fallback; a null capture disables both, preserving the
existing "unknown identity authorizes no destructive traversal" rule.

### P1 — split-read TOCTOU on PID reuse (fixed, `40f102c`)

`stillMatches()` ("is this still my process?") and `isZombie()` ("is it
dead?") were two independent reads of `/proc/<pid>/stat` per member per
sweep. A PID reuse between the two reads answers question 1 about the old
occupant and question 2 about the new one — defeating the identity
discipline the controller exists to provide.

New `ProcTree.Stat` + `ProcTree.readStat()` parse the whole line once
(identity AND state together). Steps 7 and 8 of `teardown` and the
`terminateTree` step-6 sweep now decide from one observation.
`stillMatches`/`isZombie` keep their behaviour for other callers, with a
NOTE forbidding the chained pattern.

### P1 — blocking `Thread.sleep` in coroutine teardown (fixed, `df4e132`)

`teardown()` is now `suspend`, and the default sleeper is `delay`, not
`Thread.sleep`. The old shape held its thread for up to ~2.4 s per session
(2 s reader join + 300 ms grace + 2 × 50 ms sweeps), which — now that the
owner dispatcher really is single-threaded — would serialize every other
session's close behind it; a blocking sleep also ignores cancellation.

The IME fix is the one worth spelling out: a fixed *fraction* of screen
height cannot tell a small keyboard from no keyboard. A floating/split IME
(or a one-row keyboard) holding well under 12 % read as CLOSED for the
entire time it was visible, so the console panel returned *while the user
was typing* — the v0.2 complaint, inverted. `ImeDeltaTracker` decides from
the inset's **direction** (grows → open; shrinks → closed on the first
frame, which is what the latency fix actually needed; 0 → closed;
unchanged → state retained), with deltas accumulated against the last state
change so that jitter cannot flap a stationary keyboard and a slow
animation still closes after enough small steps. No `WindowInsetsAnimation`
(API 30+): minSdk is 24 and the delta rule needs no API level.

The licence fix was larger than the review reported. `LicensesScreen`'s
`readLicenseText()` returns the **first** file that opens, and the Rust row
had `file = textmate-MIT.txt` (the VS COde Rust grammar's MIT — a
*different* component) with `file2 = Apache-2.0.txt`. So the screen rendered
the grammar's licence under Rust's name and never reached `file2` at all.
Fixed by shipping `terminal-view-Apache-2.0.txt` and a real `rust-MIT.txt`
(body verified verbatim against `rust-lang/rust@1.85.0/LICENSE-MIT`) and
repointing both rows.

## 4. Corrections to the review

Two of the review's findings were already done in the tree; it could not
read them (its own "could not check" list).

1. **The `elfStaticAarch64` fixtures exist.** The review called the
   three-fixture test "the single highest-value test missing from the
   suite" and said it would be the only thing that catches the v0.1.7
   inversion class. `ToolchainVerifierTest` contains all three —
   `busybox gate passes for a valid static AArch64 ELF`,
   `…fails with the parser diagnostic for a non-ELF file` (asserts
   `"not an ELF file"`), and `…fails for a dynamic ELF with PT_INTERP`
   (asserts `"PT_INTERP present — busybox is not static"`). They assert on
   the **public** `verify()` verdict, so they cover the call-site contract
   as well as the parser.

2. **`closeMasterFd()` is already idempotent** — `TerminalSession.java`
   guards it with `if (mMasterClosed || mTerminalFileDescriptor <= 0)
   return;` under `synchronized (this)`. The review's "make
   closeMasterFd() idempotent" was already satisfied, so the fd itself had
   that guard; the *enqueue* path did not, which is what `ba46d17` fixed.

## 5. Process failures during this cycle — recorded, not hidden

The review's meta-finding was that "verified by inspection" in commit
messages is not verification and has plausibly shipped bugs in four of the
last five releases. Two failures in this cycle demonstrate the same lesson
from the other direction, and are recorded here because a post-mortem file
that only records successes is the same failure mode in documentation
form.

1. **`ToolchainVerifier.kt` was truncated (`b4464b5`).** A *fragment* of
   the file — just the reordered `stubs` block — was passed as the write
   `content`, and the API wrote exactly what it was given, replacing an
   ~11 KB file with ~1 KB. Restored in `95c9031`. **CI caught it at the new
   `Compile check (app)` step**, failing unambiguously rather than wearing a
   test-failure mask — the process fix doing precisely what it was added
   for. Run #42 failure, run #43 success.

2. **The same mistake was attempted a second time** on `EditorScreen.kt`;
   that write was rejected on a stale SHA and so did not land. The rule
   adopted from this: **never write a file whose content was not re-read
   whole in the same session.** Whole-file writes only; no fragments.
